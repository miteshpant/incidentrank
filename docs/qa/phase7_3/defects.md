# Phase 7.3 Defects

## DEFECT-001 — Practice result screen displays wrong "Recovery Time" for every resolved outcome

- Severity: SEV-1
- Status: VERIFIED_FIXED
- Found in story: B03 (Golden-path OPTIMAL completion), while cross-checking the result screen against the `/attempts` list for D02 evidence.
- Scenario/persona/account context: `cache-node-failure`, signed in as `qa-phase73+clerk_test@example.com`, practice mode. Reproducible for every scenario and every resolved (optimal or acceptable) practice outcome, both signed-in and guest.
- Reproduction steps:
  1. Start any practice incident, apply a real fix, wait for the system to be genuinely healthy and sustained well past the point Finish becomes eligible.
  2. Wait additional wall-clock time beyond that (simulating a candidate who takes their time before clicking Finish — common, realistic behavior).
  3. Click Finish Incident, confirm.
  4. Compare the result screen's "Recovery Time" to the same attempt's "Recovery" column on `/attempts`.
- Expected: both values identical — both should reflect the moment the accepted completion tier's condition first became durably sustained-true (the value the server actually scores against and persists).
- Observed (before fix): result screen showed `02:30`; `/attempts` list (reading the persisted DB value) showed `01:40` for the identical attempt — a ~50-second, user-visible discrepancy. Confirmed as a systemic defect, not a one-off: `apps/web/src/components/scenario-console/result-screen.tsx`'s `recoveryTimeMs` computation read `state.resolvedAtMs`, which the Phase 7.1 doctrine change (`tick.ts`) made the engine *never* write for any candidate-declared completion — so every resolved result silently fell through to a client-side fallback (`state.simulationTimeMs - state.incidentStartedAtMs`, i.e. wall-clock elapsed time until the candidate happened to click Finish) instead of the server's true scoring-derived recovery time. Affected every scenario using `GenericResultScreen` (all 99 generic-console scenarios) and Payment Retry Storm's own hand-written console (same shared hook/component) — i.e. every practice attempt in the product, signed-in or guest. The assessment side was unaffected (its result screen is neutral/zero-props per the separate Phase 7.1 privacy work, so recovery time is never shown to assessment candidates at all).
- Root cause: a pre-existing (Phase 6.1) client-side fallback formula that was silently exercised for the first time once Phase 7.1 removed the engine's own `resolvedAtMs` write — exactly the same class of "newly exercised timing discrepancy" documented for the 17 migrated scenario *tests* this phase, except this instance leaked into live UI display rather than being caught by a test assertion, because no test asserted on the displayed Recovery Time value specifically.
- Fix: threaded the server's already-correctly-computed `recoveryTimeMs` (same formula `persistTerminalAttempt` persists and scores against, derived via `deriveScoringResolvedAtMs`) through to the client for a resolved outcome: added `recoveryTimeMs` to `FinishResult` (`apps/web/src/lib/server/finish-attempt.ts`, both the fresh-persist and retry-rebuild-from-row paths), to the `/api/attempts/[attemptId]/finish` and `/api/attempts/finish-preview` route responses, to `FinishResponse`/`requestFinish`/`requestFinishPreview` (`apps/web/src/lib/attempt-persistence.ts`), to `useIncidentAttempt`'s new `serverRecoveryTimeMs` return field (`apps/web/src/lib/use-incident-attempt.ts`), and finally to `GenericResultScreen`'s new `serverRecoveryTimeMs` prop (`apps/web/src/components/scenario-console/result-screen.tsx`), which now prefers it over the client-side formula whenever the outcome is resolved. Both consumers of `GenericResultScreen` (`generic-incident-console.tsx` and `payment-retry-storm/incident-console.tsx`) updated to pass the new prop through. A failed outcome is untouched — `state.failedAtMs` is still genuinely engine-written (failure remains automatic), so its existing client-side formula was already correct and needed no change; `score-preview`'s automatic-failure-only retry path also needed no change for the same reason.
- Regression test added: `apps/web/src/components/scenario-console/generic-incident-console.test.tsx` — new test asserting the displayed Recovery Time matches a server-provided `recoveryTimeMs` (`00:12`) even when the candidate waits 90+ simulated seconds past that point before clicking Finish, and explicitly asserting the old wrong wall-clock-derived value range is absent.
- Retest evidence: reproduced live in the browser against the fixed code (hot-reloaded dev server) — result screen showed "Recovery Time 00:38", and the persisted `/attempts` list for the same attempt showed "00:38" in the Recovery column — exact match. Re-ran full `apps/web` test suite (266/266 passed, including the new regression test) and `pnpm --filter @incidentrank/web lint`/`typecheck` (clean).

## DEFECT-002 — Refreshing/revisiting an active practice incident silently creates a duplicate attempt and orphans the original

- Severity: SEV-1
- Status: VERIFIED_FIXED
- Found in story: C01 (refresh during active incident), while investigating why the briefing screen reappeared instead of resuming.
- Scenario/persona/account context: `cache-node-failure`, signed in as `qa-phase73+clerk_test@example.com`, practice mode. Reproducible for every scenario (both `GenericIncidentConsole`, used by 99 of 100 built-in scenarios, and Payment Retry Storm's own hand-written console) and every signed-in practice attempt — anonymous/guest practice is unaffected (guest attempts are never persisted at all).
- Reproduction steps:
  1. Sign in, start a practice incident, apply at least one control change.
  2. Navigate away (e.g. to `/attempts`) or refresh the page.
  3. Navigate back to `/incidents/<slug>` and click Acknowledge Incident again.
  4. Check `/attempts` — count rows for this scenario with outcome "In Progress."
- Expected: the candidate returns to their existing in-progress incident, with prior actions/reasoning restored (per spec C01: "same attempt resumes... no new attempt is silently created").
- Observed (before fix): revisiting `/incidents/<slug>` always rendered a fresh, empty briefing screen — there was no resume affordance anywhere in the product (not on the scenario page, not on the read-only `/attempts/[attemptId]` detail page, which has no Resume/Continue link at all). Re-acknowledging created a second "In Progress" row for the same scenario in `/attempts`, permanently orphaning the first — confirmed directly: before re-acknowledge, exactly 1 "In Progress" `Cache Node Failure` row existed; after, 2. The orphaned attempt's persisted data (actions, timeline) was intact and correct when inspected via `/attempts/[attemptId]` — this was a reachability/resume defect, not data loss, but functionally equivalent to "active attempt lost on refresh" (spec's own SEV-1 example) since the candidate had no way back into it.
- Root cause: `apps/web/src/lib/use-incident-attempt.ts`'s attempt-creation effect (`POST /api/attempts`) fires unconditionally whenever a signed-in candidate acknowledges a fresh briefing, with no check for an existing in-progress attempt for that user+scenario. Separately, `GenericIncidentConsole` and Payment Retry Storm's `IncidentConsole` never passed a `resumeSeed`/`initialAttemptId` into the hook at all — despite the hook, its reducer's `"paused"` phase, and a full server-side resume-reconstruction pipeline (`apps/web/src/lib/server/attempt-resume.ts`'s `loadResumeData`, exposed at `GET /api/attempts/[attemptId]/resume`, with 12 passing integration tests in `attempt-resume.test.ts`) already existing and already correctly described in their own doc comments as built for exactly this "candidate refresh/return flow" — the practice UI simply never called any of it. This was dead, unwired, already-tested infrastructure, not a regression.
- Fix: two parts.
  1. **Idempotency at the source**: `POST /api/attempts` (`apps/web/src/app/api/attempts/route.ts`) now checks for an existing `in_progress` practice attempt for the same user+scenario before inserting, and returns that row instead of creating a duplicate.
  2. **Actual resume UX**: `GenericIncidentConsole` (`apps/web/src/components/scenario-console/generic-incident-console.tsx`) and Payment Retry Storm's `IncidentConsole` (`apps/web/src/app/incidents/payment-retry-storm/incident-console.tsx`) now perform a resume lookup on mount for signed-in candidates — `GET /api/attempts?scenarioSlug=<slug>` (new scoped-query branch added to the existing route's `GET` handler) finds an existing in-progress attempt, and if one exists, `GET /api/attempts/[attemptId]/resume` (already built, now finally called) reconstructs a full `ResumeSeed`. The hook mounts directly with that seed rather than a fresh briefing, landing in its existing `"paused"` phase; a new `GenericResumeScreen` component (`apps/web/src/components/scenario-console/resume-screen.tsx`, mirroring the existing assessment-only `resume-screen.tsx`'s "do not auto-restart the timer before the candidate explicitly resumes" principle) renders a "Resume Incident" prompt before the clock restarts. Two new client helpers added to `attempt-persistence.ts`: `findActiveAttempt` and `fetchResumeSeed`. `toTimelineEntries` exported from `use-incident-attempt.ts` for reuse rather than duplicated.
- Regression test added: `apps/web/src/app/api/attempts/route.test.ts` — new describe block, 5 tests: a second POST for the same scenario returns the existing attempt (not a new row, exactly 1 row persisted); a different scenario still gets its own new attempt; `GET ?scenarioSlug=` finds the existing in-progress attempt; returns null when none exists; unscoped `GET` (no query param) still returns the full history list unaffected. Also fixed 3 pre-existing component tests (`persistence.test.tsx` ×3, `feedback-retry.test.tsx` ×2) that needed an extra `await act()` + a mock response for the new `GET ?scenarioSlug=` lookup, since the resume-lookup gate is now a real async step before the briefing screen renders for signed-in tests.
- Retest evidence: reproduced live against the fixed code. Revisiting `/incidents/cache-node-failure` (an attempt orphaned before the fix existed) rendered "INCIDENT IN PROGRESS / Your incident is currently paused at 00:48 / Your previous actions and reasoning have been restored." instead of a fresh briefing. Clicking Resume Incident restored the live console with the correct historical timeline entry ("00:35 YOU — Cache Node Count changed 3 → 4") intact and not duplicated. Finishing from the resumed state produced a correct result (955/1000); `/attempts` afterward showed that same row now `completed`, not a second row. Full `apps/web` test suite rerun green (266/266 before the new tests, confirmed 10/10 passing in `route.test.ts` including the 5 new ones), lint/typecheck clean.

## DEFECT-003 — Candidate's own "Your Attempts" history list leaks assessment score, outcome, and recovery time

- Severity: SEV-0
- Status: VERIFIED_FIXED
- Found in story: E08 (candidate attempts practice-result route patterns), discovered live after completing a real company assessment end-to-end as the actual invited candidate — the single highest-value check this phase performed.
- Scenario/persona/account context: signed in as the real candidate account (`qa-phase73-candidate+clerk_test@example.com`), having just legitimately completed and submitted a company assessment (`cache-node-failure`, via a real invite flow through a real organization/assessment created for this QA pass).
- Reproduction steps:
  1. As a candidate, accept a real assessment invite, complete the assessment, and submit (confirmed the submission screen itself was correctly neutral — "Assessment submitted successfully. Results are available to the hiring organization.").
  2. Navigate to `/attempts` (the candidate's own personal attempt-history page, reachable via the top nav "Attempts" link — not a hidden or unusual route).
- Expected: the assessment attempt should appear with no score/outcome/recovery-time, matching the same redaction already correctly applied to the Finish response, the direct `GET /api/attempts/[attemptId]` API, and the practice `/attempts/[attemptId]` detail page.
- Observed (before fix): the list row showed **"Cache Node Failure · 10/25/2026 · 905 / 1000 · completed · 01:20"** — the full total score, a raw `status` value ("completed", distinct from the candidate-safe "submitted" boolean used everywhere else), and the exact recovery time, all directly visible to the candidate for their own company assessment. Clicking into the same attempt's detail page (`/attempts/[attemptId]`) correctly showed the redacted "This was a company assessment attempt. Results are available to the hiring organization, not shown here." message — confirming the leak was isolated to the list view, not the detail view, and that the already-existing privacy work elsewhere was otherwise intact.
- Root cause: `apps/web/src/app/attempts/attempts-list.tsx` (`AttemptsList`, the server component backing `/attempts`) queried the raw `attempts` table directly and rendered `attempt.score`/`attempt.status`/`attempt.recoveryTimeMs` unconditionally for every row, with no `attemptType` branching and no call to the already-existing shared `redactAttemptForCandidate` helper that every other candidate-facing attempt surface uses. This list route was simply never covered by the original Phase 7.1 privacy-surface audit (which enumerated exactly four surfaces: the Finish response, the attempt GET API, the practice attempt-detail page, and the assessment result screen — this list was surface #5, never identified).
- Fix: `attempts-list.tsx` now calls `redactAttemptForCandidate(attempt)` per row and branches rendering on the result's `attemptType` — an assessment row renders `—` / `"Submitted"` or `"In Progress"` / `—` for Score/Outcome/Recovery; a practice row renders exactly as before (unaffected). No schema or query change — purely a response/render-layer fix, consistent with how every other surface in this privacy model was fixed.
- Regression test added: `apps/web/src/app/attempts/attempts-list.test.tsx` — new file, 2 tests, DB-integration style mirroring `attempt-privacy.route.test.ts`'s existing pattern: inserts a fully-scored assessment attempt row directly and asserts the rendered DOM contains "Submitted" but not the score, "1000", the recovery time, or the raw "completed" status text; a second test inserts a practice attempt row and asserts its score/recovery time DO render, proving the fix didn't over-redact.
- Retest evidence: reproduced live against the fixed code (hot-reloaded dev server) as the real candidate account — `/attempts` now shows "Cache Node Failure · 10/25/2026 · — · Submitted · —" for the same real assessment attempt. Re-ran `apps/web` typecheck/lint (clean) and the new test file (2/2 passed).

## DEFECT-004 — All 100 scenarios' simulation/scoring logic ships in one shared client bundle, not scoped per-scenario

- Severity: SEV-2
- Status: DEFERRED (explicitly accepted with rationale, per spec's SEV-2 policy)
- Found in story: G04 (scenario solution/golden-path isolation), via build/bundle inspection.
- Scenario/persona/account context: fully unauthenticated (`credentials: "omit"`) fetch of the client JS chunk served when visiting any single scenario page (e.g. the free `database-connection-saturation`).
- Reproduction steps:
  1. As an anonymous, signed-out visitor, load any one scenario page (e.g. `/incidents/database-connection-saturation`).
  2. Collect the `<script src="...">` tags from the page HTML; fetch each with `credentials: "omit"`.
  3. Grep the fetched source for other scenarios' slugs/logic, e.g. `enterprise-wide-dependency-deprecation` (a locked, Principal-tier PAID scenario never visited this session).
- Expected (per spec G04): candidate-facing bundles/APIs must not expose golden-path fixtures, expected-optimal controls, or scenario-solution internals beyond the one scenario intentionally being practiced. The `golden-paths` directory specifically must stay test-only/internal.
- Observed: confirmed the `golden-paths` directory itself is correctly never leaked — it is never exported from `packages/scenarios/src/index.ts` and no client-served chunk anywhere contains `GOLDEN_PATHS`/`goldenPath`/`ScenarioGoldenPath` (checked across all 28 scripts referenced by a scenario page). However, one shared chunk (`packages_scenarios_src_<hash>._.js`, ~6.4MB) bundles the full `successCondition`, `failureCondition`, and `actionClassifications` (the exact harmful/beneficial/neutral control classification logic) source for **all 100 scenarios simultaneously** — confirmed 102 distinct `packages/scenarios/src/<slug>/` directories referenced in one chunk, including scenarios the visitor has never unlocked or even viewed (e.g. the locked `enterprise-wide-dependency-deprecation`). This chunk is served with no auth check (plain static asset), so any anonymous visitor who loads one free scenario receives the exact solution-classification logic for every paid/locked scenario too.
- Root cause: the client-side live simulator genuinely needs to run `simulate()`/`tick()` in-browser for the scenario actively being practiced (confirmed architectural requirement — `apps/web/src/lib/use-incident-attempt.ts` imports `simulate` from `@incidentrank/simulator` directly, and scoring is still server-authoritative/re-validated at Finish regardless, per the binding Phase 6.1 "Client scoring removed" decision — this is not a scoring-integrity defect). The actual gap is that `packages/scenarios/src/index.ts` statically barrel-exports all 100 scenario definitions from one module with no code-splitting, and nothing in `apps/web`'s build config (`next.config.ts` has no custom chunking strategy) or scenario-loading call sites (`scenario-registry.ts`, `generic-incident-console.tsx`, etc.) lazily imports a single scenario by slug — so Turbopack/webpack has no boundary to split on, and the whole package collapses into one shared chunk included on every scenario page.
- Fix: not implemented this phase. A correct fix requires converting `@incidentrank/scenarios`'s catalog resolution to genuine per-scenario dynamic `import()` (keyed by slug) threaded through `scenario-registry.ts` and every console/preview call site that currently assumes synchronous, eagerly-available `ScenarioDefinition` access — a cross-cutting client-loading-architecture change, not a contained bug fix. This falls outside Phase 7.3's explicit scope boundary (the spec's "redesign of all 100 incidents" exclusion is the closest-matching deferred-work category; this is a loading-strategy change touching all 100 scenario modules' consumption pattern, not their content).
- Rationale for accepting as deferred rather than blocking phase completion: (1) this is a content/IP-isolation gap, not an access-control bypass — it does not let any user play, start, or get credit for a locked scenario (G01/G02/G03's actual access boundaries are confirmed solid and unaffected); (2) exploiting it requires manually fetching and reading minified bundle source — no UI surface or documented API exposes it; (3) scoring remains fully server-authoritative regardless of what classification logic is readable client-side, so this cannot be used to forge a better score (consistent with the existing golden-path harness and Phase 6.1 client-scoring-removal guarantees); (4) a correct fix is a genuine architecture change (dynamic per-scenario loading) with real regression risk across every scenario-console call site, appropriately scoped to a dedicated follow-up rather than squeezed into a QA phase.
- Regression test added: none (deferred, not fixed).
- Retest evidence: not applicable (deferred). Recommend tracking as a follow-up: "lazy-load scenario simulation modules by slug" — out of scope for Phase 7.3, suitable for a dedicated future phase.

## DEFECT-005 — Finish Incident confirmation dialog never receives keyboard focus, and Escape does not close it

- Severity: SEV-2
- Status: VERIFIED_FIXED
- Found in story: J (accessibility sanity checks), testing Escape behavior and focus states on the primary Finish flow.
- Scenario/persona/account context: any practice attempt (confirmed on `database-connection-saturation` and `kafka-consumer-lag`); the shared `FinishIncidentDialog` component is used identically by practice, Payment Retry Storm's own console, and the assessment console, so this affected all three.
- Reproduction steps:
  1. Start any incident, let it begin, and open the Finish Incident confirmation dialog (keyboard or mouse).
  2. Inspect `document.activeElement`.
  3. Press Escape.
- Expected (per spec Group J): "Escape behavior on Incident Brief/dialogs" and "modal/dialog focus is not obviously broken" — opening a modal dialog should move focus into it, and Escape should close it, consistent with the Incident Brief drawer's own already-correct behavior elsewhere in this same codebase.
- Observed (before fix): `document.activeElement` remained `<body>` after the dialog opened — focus was never moved into the dialog despite it having correct `role="dialog"`/`aria-modal="true"`/`aria-labelledby` markup. Because focus stayed outside the dialog, pressing Escape did nothing (no listener was scoped to receive it) — the dialog stayed open and the only way to dismiss it was a mouse click on "Keep Working." A screen-reader user would not be announced into the dialog at all when it opened.
- Root cause: `apps/web/src/components/scenario-console/finish-incident-dialog.tsx` had correct ARIA attributes but no focus-management `useEffect` and no Escape `keydown` listener — unlike `apps/web/src/components/scenario-console/incident-brief.tsx` (the Incident Brief drawer, built earlier in Phase 7.1), which already implements exactly this pattern correctly (`closeButtonRef.current?.focus()` on open, a `keydown` listener calling `onClose()` on Escape). The Finish dialog was simply never given the same treatment when it was built.
- Fix: added the identical pattern to `FinishIncidentDialog` — a `cancelButtonRef` on the "Keep Working" button, a `useEffect` that focuses it when `open` becomes true, and a `useEffect` registering a `document`-level `keydown` listener (only while open) that calls `onCancel()` on Escape, cleaned up on unmount/close. No visual/layout change — purely focus and keyboard behavior.
- Regression test added: `apps/web/src/components/scenario-console/finish-incident-dialog.test.tsx` (new file), 3 tests: focus lands on "Keep Working" when `open` becomes true; Escape calls `onCancel` and never `onConfirm`; while `open={false}`, Escape does nothing (no stray global listener firing when the dialog isn't mounted).
- Retest evidence: reproduced live against the fixed code (hot-reloaded dev server) on a real `kafka-consumer-lag` attempt — opening Finish Incident now lands keyboard focus on "Keep Working" (confirmed via `document.activeElement`), and pressing Escape correctly closes the dialog (confirmed the dialog element is removed from the DOM) without ending the incident. Full `apps/web` test suite rerun green (276/276, up from 273 — the 3 new tests), lint/typecheck clean.
