# Scenario — Payment Retry Storm

## Purpose

Payment Retry Storm is IncidentRank's first complete scenario. It proves that
an authored production incident can respond meaningfully to different
candidate decisions, using only structured controls (no free text, no AI
evaluation) and a deterministic engine.

The candidate is on-call for a checkout system. A payment provider begins
degrading, and the existing retry configuration amplifies the problem. The
candidate must diagnose and mitigate the incident using the controls
available to them.

> The numeric metrics in this scenario are authored to communicate realistic
> system behavior. They are not generated by an infrastructure performance
> model.

## Architecture

```text
Client
  ↓
API Gateway
  ↓
Checkout Service
  ↓
Payment Service ─────→ External Payment Provider
  ↓
Postgres
  ↓
Kafka
  ↓
Settlement Worker
```

Each component exposes a simple authored health value (`healthy` / `degraded`
/ `critical`) that changes as a side effect of whichever rule is currently
matched — never computed from a formula.

## Initial State

Before the incident begins (T=0 to T=60s):

```text
status                    healthy
checkout success          99.9%
checkout P99               420ms
payment provider latency   180ms
payment traffic           normal
db pressure               normal
kafka lag                 0
revenue loss               $0
```

## Incident Event

At **T=60s**, the external payment provider degrades. This is a timed event,
not something the candidate triggers. The scenario emits `PROVIDER_DEGRADED`
and, because the default configuration (`retries=3`, `backoff=none`,
`circuitBreaker=off`) amplifies the problem, checkout immediately becomes
critical:

```text
checkout success           72%
checkout P99               6.4s
payment provider latency    4.8s
payment traffic            critical
db pressure                critical
kafka lag                   18,000
status                      critical
```

The candidate is never told the root cause directly. They must infer "payment
provider retry storm" from the observable metrics and architecture.

## Available Controls

| Control | Key | Allowed values | Initial |
|---|---|---|---|
| Retries | `retries` | 0, 1, 3, 5 | 3 |
| Backoff | `backoff` | none, fixed, exponential | none |
| Circuit breaker | `circuitBreaker` | off, on | off |
| Timeout | `timeoutSeconds` | 1, 2, 3, 5 | 2 |
| Payment instances | `paymentInstances` | 4, 8, 12, 16, 24 | 8 |
| Checkout instances | `checkoutInstances` | 4, 8, 12, 16, 24 | 8 |
| DB connection limit | `dbConnectionLimit` | 250, 500, 750, 1000 | 500 |
| Kafka settlement consumers | `kafkaConsumers` | 4, 8, 12, 16, 24 | 8 |

Invalid values (e.g. `retries=4`, `timeoutSeconds=4500`,
`paymentInstances=7`) are rejected outright — the engine never silently
clamps a candidate's input.

## System-Design Concepts Tested

- Retry storms and positive feedback loops in distributed systems
- Backoff strategies as a mitigation for retry amplification
- Circuit breakers: protecting a downstream dependency at the cost of
  fail-fast failures, not a silver bullet
- Timeout tuning as a tradeoff between latency and success rate, not a
  universally "correct" value
- Scaling the caller (Checkout, Payment) vs. fixing the actual dependency
  (the external provider) — scaling Checkout does nothing for a payment
  provider outage; scaling Payment aggressively while retries stay high
  makes the retry storm *worse*, not better
- Kafka consumer scaling affects settlement backlog but is orthogonal to
  checkout health
- DB connection limits trade a small reduction in connection pressure for
  increased infrastructure cost, without touching the root cause

## Major Authored Consequences (Rule Paths)

Rules are evaluated in authored order, most-specific match wins. All values
below are fixed, authored snapshots — never derived from a formula.

| Path | Condition (while provider degraded) | Checkout success | P99 | Notes |
|---|---|---|---|---|
| A (default) | retries ≥ 3, backoff none | 72% | 6.4s | Baseline critical incident |
| A (worse) | retries = 5 | 63% | 7.8s | Increasing retries makes it worse |
| Aggressive scaling | retries ≥ 3 and paymentInstances ≥ 16 | 58% | 8.2s | Scaling the caller while retries stay high amplifies the storm further; can trigger failure |
| Low timeout | timeoutSeconds ≤ 1 | 66% | 2.2s | Fails fast: P99 improves, success worsens |
| High timeout | timeoutSeconds ≥ 5 | 74% | 7.2s | Requests tie up longer: P99 worsens, success improves slightly |
| B | retries ≤ 1 | 84% | 4.2s | Improved, not resolved |
| C | retries ≤ 1 and backoff = exponential | 92% | 2.8s | Further improved |
| D (poor retries) | circuitBreaker = on (retries not yet reduced) | 82% | 1.2s | Protects downstream, but fail-fast traffic caps success |
| Good recovery | circuitBreaker = on, backoff = exponential, retries ≤ 1 | 96% | 1.6s | Stable enough to resolve if sustained |

Multiple other combinations can still reach the "good recovery" rule — the
condition is retries ≤ 1 AND backoff = exponential AND circuit breaker on; the
exact path taken to get there (which control changed first, whether timeout
was also adjusted) does not matter.

## Scaling and Infrastructure Cost

Scaling is authored to be a real, usable tradeoff:

- Checkout instances: modest cost, does not touch the root cause.
- Payment instances: cheap at first, but made *harmful* once retries are
  still high (compounds the retry storm instead of fixing it).
- Kafka settlement consumers: reduces backlog only, never touches checkout.
- DB connection limit: higher limits cost more and do not resolve the
  checkout incident on their own.

Monthly infrastructure cost starts at **$20,000** and increases with each
scaled control, using authored per-unit increments (see
`packages/scenarios/src/payment-retry-storm/revenue-and-cost.ts`).

## Incident Timeline

1. **00:00** — System healthy.
2. **01:00** — Provider degrades; checkout drops to critical.
3. Candidate investigates and begins making changes.
4. Each accepted change emits `CONFIG_CHANGED` with `target`, `field`,
   `previousValue`, `newValue`.
5. As metrics cross authored thresholds, the engine emits transition-only
   events (`CHECKOUT_CRITICAL` / `CHECKOUT_RECOVERING`,
   `DB_PRESSURE_CRITICAL` / `DB_PRESSURE_RECOVERED`,
   `KAFKA_BACKLOG_HIGH` / `KAFKA_BACKLOG_RECOVERED`).
6. If the candidate reaches and holds a qualifying configuration, the engine
   emits `INCIDENT_RESOLVED` after the metrics are sustained for 30 seconds.

## Success Conditions

The incident resolves once, for **30 consecutive simulated seconds**:

```text
checkout success rate   >= 95%
checkout P99 latency    <= 3,000ms
payment traffic          not critical
db pressure              not critical
```

Kafka lag does **not** need to reach zero to resolve — it is tracked
separately as a scoring input.

## Failure Condition

If checkout success rate stays **below 60%** for **3 consecutive simulated
minutes** after the incident has started, the attempt is marked `failed`.
This can happen from "brute-force" bad configurations, such as scaling
Payment instances aggressively while retries remain high.

## Natural Provider Recovery

If the candidate does nothing, the provider begins recovering at **T=12
minutes** and is fully healthy by **T=15 minutes**. Doing nothing therefore
eventually "resolves" the incident, but at a much higher cost: a long
recovery time, maximal revenue loss, and the maximum possible time spent in
a critical state.

## Scoring Inputs Tracked

The engine does not calculate a 0–1000 score in this phase. It tracks the raw
inputs a future scoring phase will need:

```text
incidentStartedAtMs / resolvedAtMs / failedAtMs
totalTimeInCriticalMs / totalTimeInDegradedMs
revenueLossUsd
peakSeverityRank
numberOfConfigurationChanges
numberOfHarmfulChanges / numberOfBeneficialChanges
initial / final / peak monthly infrastructure cost
final / peak Kafka lag messages
```

"Harmful" and "beneficial" are authored per control+value in
`action-classifications.ts` — never inferred mathematically or by an AI
judgment call.

## Known Simplifications

- Metrics are authored snapshots per matched rule, not derived from queueing
  theory, throughput equations, or any infrastructure performance model.
- The rule table is a finite, ordered list of conditions. It covers the
  narrative paths in the specification plus the timeout tradeoff and
  harmful-scaling cases, but is not an exhaustive cross-product of every
  possible control combination — combinations not explicitly authored fall
  through to the closest matching (typically the default critical) rule.
- Revenue loss and infrastructure cost use simple per-minute / per-unit
  authored rates, not real accounting or cloud pricing.
